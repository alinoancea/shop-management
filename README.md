# Product Catalog – DBF to SQLite Sync

A web application that parses local DBF files, stores products in SQLite, and exposes a searchable web interface and API.

## Features

- **DBF parsing**: Reads one or more `*.dbf` files from a configurable folder
- **SQLite storage**: Products are stored locally, unique by barcode
- **Auto-sync**: Parses DBF files every 5 minutes
- **Web UI**: Bootstrap-based, searchable product list
- **REST API**: List, search, and get products by barcode

## Setup

### 1. Install dependencies

```bash
pip install -r requirements.txt
```

### 2. Configure (optional)

Set environment variables or edit `config.py`:

| Variable | Default | Description |
|----------|---------|-------------|
| `BARCODE_COLUMN` | `BARCODE` | DBF column with product barcode |
| `NAME_COLUMN` | *(auto)* | DBF column for product name |
| `DATABASE_PATH` | `products.db` | SQLite database path |
| `PARSE_INTERVAL_MINUTES` | `5` | Sync interval in minutes |

### 3. Add DBF files

Open **Settings** (gear icon) in the web UI and add the full paths to your `.dbf` files. Paths are saved to `settings.json` and persist across restarts.

### 4. Run the application

```bash
python app.py
```

- **Web interface**: http://127.0.0.1:18766
- **API**: http://127.0.0.1:18766/api/products

`python app.py` serves the app with [waitress](https://docs.pylonsproject.org/projects/waitress/) (a production
WSGI server that works on Windows) and starts the DBF sync in the background. With `FLASK_DEBUG=1` it uses Flask's
development server instead, with auto-reload; the same happens if waitress is not installed (a warning says so).

By default the server listens on `0.0.0.0:18766`, i.e. on every network interface, so screens and other PCs on the
network can connect. There is no login: keep it on the local network. To allow only the machine it runs on, or to
change the port, set environment variables before starting it
(PowerShell: `$env:APP_HOST = "127.0.0.1"; python app.py`):

| Variable | Default | Description |
|----------|---------|-------------|
| `APP_HOST` | `0.0.0.0` | Address to listen on. `0.0.0.0` = every network interface, `127.0.0.1` = this machine only |
| `APP_PORT` | `18766` | Port to listen on. If it is already taken, the app stops with a message: choose another port |

Screens then use `http://<machine-IP>:<port>`, e.g. `http://192.168.1.10:18766`.

## API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/products` | List products. Query params: `q` (search), `limit`, `offset` |
| GET | `/api/products/<barcode>` | Get product by barcode |
| POST | `/api/sync` | Trigger manual DBF sync |
| GET | `/json_items` | Products for display devices. Optional `gama` (an app-defined identifier or a DBF gama value): returns `{"<gama>": [...]}`, otherwise a plain list |

## Store name and version

The left menu shows the store name under the app title (set in **Setări**, up to 60 characters, optional) and the
app version at the bottom (`APP_VERSION` in `config.py`, bump it when you release a change).

## Gamas

Gamas are defined in the web UI (**Configurare game**). A gama has:

- an **identifier**, generated by the server (6 characters, e.g. `K7M2QX`). It is never chosen by the user and never changes,
- a **title** (not unique; this is what the screen configuration shows),
- an optional **DBF gama**: when set, the gama contains every product of that DBF gama,
- **products added by hand**, on top of the DBF ones. A product appears once per gama and can be in any number of gamas.

A gama can't be deleted while a screen has a block on it. An app-defined gama wins over a raw DBF value
with the same name; DBF gama values without a definition can still be used as they are.

## Screen devices

Screens are configured in the web UI (**Configurare ecrane**) and pull their configuration from the server.
A screen shows 1 or 2 blocks; each block has a gama (identifier), a title and a width (columns out of 6).
Layouts: `6`, `3+3`, `2+4`, `4+2` (blocks go left to right).

Device protocol:

1. **First start** (no stored id): `POST /api/screens/register` -> `201 {"id": 7}`. Store the id on disk and use it from now on. While the screen is not configured, show the id so it can be recognised in the UI. The id can also be typed in by hand to take over an existing screen (e.g. a replacement device).
2. **Every `refresh_seconds`**: `GET /json_screen/<id>`. Keep showing the last good response if the server is unreachable.
3. `404` means the id is unknown (the screen was deleted): register again or show an error.

```json
{
  "id": 7,
  "name": "Raft mezeluri",
  "configured": true,
  "layout": "2+4",
  "refresh_seconds": 60,
  "blocks": [
    {"title": "Mezeluri", "gama": "MEZELURI", "width": 2,
     "items": [{"barcode": "5900000000001", "name": "Salam", "um": "BUC", "price": 10.5, "quantity": 3.0}]},
    {"title": "Fructe", "gama": "FRUCTE", "width": 4, "items": []}
  ]
}
```

An unconfigured screen gets `"configured": false`, `"layout": null` and `"blocks": []`.
`refresh_seconds` is set in **Setări** (10-3600, default 60).

Self-check for this API: `python test_screens.py`.

## DBF column mapping

The parser auto-detects barcode columns from common names: `BARCODE`, `EAN`, `CODE`, `ARTICLE`, `ARTNR`, `SKU`, `PLU`. Override with `BARCODE_COLUMN` if your column has a different name.
